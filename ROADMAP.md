# Gyges Roadmap

> Drafted 2026-10-20 from `OVERVIEW.md` §7. Milestones are ordered by risk retired per unit of work; each later milestone has its own design note before code starts.

## Principles

- **Core loop first.** Nothing ships until init → sync → send → confirm works end to end on regtest against a real `zakurad`. Everything else is layered on top of that loop.
- **Track Zakura deliberately.** Exact pins, `Cargo.lock` committed, one PR per upstream release, regtest suite green before merge (`OVERVIEW.md` Q-D3).
- **Pools are data.** Orchard, Ironwood and transparent spend in the MVP; Sapling receive-only. Ironwood cannot be "off": after NU6.3 (regtest height 1, mainnet 3,428,143) the wallet libraries build every shielded output in the Ironwood pool and the ZIP 318 turnstile keeps value out of Orchard, so Orchard is spend-only there (Q-D7, `OVERVIEW.md` §4.3).
- **Security claims are tested.** Every control in `THREAT_MODEL.md` names the test that proves it (`TESTING.md`).

### M1 leftovers

The exit criterion is met. These gaps were recorded under "Not done" in the items above and had no checkbox of their own; none blocks M2 or M4.

- [x] Mempool loop (`SYNC.md` §7): `getrawmempool` diff per poll tick, trial decryption into **Pending Confirmation** in `balance`, `gyges sync mempool`. Landed as:

  - `gyges sync mempool` prints `scanned N transactions, found M notes`.

- [x] Mined status for fully transparent transactions without change: no `TransactionDataRequest::GetStatus` in rc9.1, so mark them from the node's `getrawtransaction` with `set_transaction_status`, as the `TexQueue` already does for a transparent step 2.

  The premise was half right. rc9.1 has no `GetStatus` data request, but upstream already queues a status lookup for every sent transaction that scanning cannot see, behind `TransactionStatusRead::transaction_status_work()`. That call failed with `StatusModeNotConfigured`, because gyges never chose a status mode (`OVERVIEW.md` §4.3). Landed as:
  - `registry::open_wallet` selects `TransactionStatusMode::Public` next to the transparent ledger mode.
  - `gyges_core::sync::{pending_status, upstream_status, record_status}`. `Mined(h)` stays `Mined(h)`; `InMempool` becomes `NotInMainChain`, which keeps the lookup queued until expiry; `Unknown` becomes `TxidNotRecognized`.
  - `gygesd::sync::Scheduler::check_status`. After each key's step it asks the node about the queued txids, at most once per `poll_interval_secs` per key. It never runs during a backfill, so the fallback endpoint is never asked about the wallet's own txids. A `Mined` height above the key's scanned tip waits until the scan reaches it.

  `wait_for_mined`, `WaitSync { txid }` and `tx list` read the recorded height, so they now see these transactions. Before this change `wait_for_mined` never ended for them.

  **Fixed on the way:** `max` from a wallet whose spendable value is all transparent failed with `INSUFFICIENT_FUNDS`. Upstream reports `available = 0` for such a selection, and `propose_send`'s fee loop subtracted the whole amount. It now subtracts the fee from the wallet's own spendable total.

  Tests: `rpc.rs::a_fully_transparent_send_is_marked_mined_from_the_node`. A transparent-only wallet sends `max` to a `t` address. The proposal has only transparent inputs and outputs, and the txid is queued for a status lookup after the broadcast. The stream ends with `mined` at the block that holds it, `WaitSync` on the txid returns, the queue is empty and the balance is zero. With the status pass disabled, the stream never ends (checked). There is also a unit test of the status mapping.

  Not done:
  - A transparent-only transaction whose block the node pruned before the daemon asked: the node answers `Unknown`, so the wallet treats it as unmined until it expires. Asking the fallback endpoint instead would disclose the txid to it.
  - The real-node scenario.
- [x] `TESTING.md` §3 rows 16 (`daemon stop` mid-scan, restart resumes without rescanning) and 17 (one `getblock` per block across three keys).

  Row 16 found that shutdown did not wait for the batch in hand. It aborted the scheduler task without awaiting it, then checkpointed the cache while the batch's `spawn_blocking` scan could still be running. It also unlinked the socket first, so `daemon stop` returned before any of that finished. `gyges daemon stop --help` ("finish the current batch") was therefore not true. Landed as:
  - `SyncHub::request_stop`. The scheduler checks it between ticks and between keys, so it finishes the batch in hand (fetch and scan) and returns.
  - `Daemon::serve` waits for the scheduler for up to 30 s (`SCHEDULER_STOP_GRACE`) before cancelling it, then zeroizes, checkpoints, and unlinks the socket last.
  - SYNC.md §8 now says the wallet databases use a rollback journal, so only `blocks.sqlite` is checkpointed.
  - `FakeNode::{hold_after_raw_blocks, release, held_requests}` stall the node in the middle of a scan, deterministically.

  Tests:
  - Row 16, `rpc.rs::daemon_stop_mid_scan_finishes_the_batch_and_restart_does_not_rescan`. Exactly one batch is committed after the stop is asked for, and the wallet's max scanned height equals the last logged batch end. The cache WAL is empty, and after a restart no range is scanned twice. With the old abort put back, the test fails (checked).
  - Row 17, `rpc.rs::three_keys_fetch_each_block_from_the_node_once`. Three keys over 60 blocks cost exactly 120 `getblock` calls, two per block. The count comes from the fake node's call log instead of a harness proxy.

  Not done: both rows run in-process against the fake node only, not through the binaries or against `zakurad`.

## M2 — Historical restore over Tor

Design note: `SYNC.md` §Case B.

- [x] `ArtiTorLwdBackend` on `zcash_client_backend::tor`; `GetSubtreeRoots`, `GetBlockRange` streaming into the shared cache. Landed as `gyges_chain::lwd::ArtiTorLwdBackend`, a second `ChainBackend` over a lightwalletd / zaino `CompactTxStreamer` endpoint: `GetLatestBlock` as the bounds (`retained_from = 0`), `GetBlock`, `GetTreeState`, `GetBlockRange` collected per `cache.fetch_batch`-sized call with an idle timeout and checked for the exact heights, 32-byte hashes and `prev_hash` links (a skipped, forked or overlong stream is refused, a short one is `BlockUnavailable`, a stalled one `Unreachable` and the connection dropped), `GetSubtreeRoots`, `SendTransaction` (for `--via-tor`), `GetTransaction` for `transaction_status`, and `GetLightdInfo` once per connection to refuse an endpoint for another chain. Tests: an in-process fake `CompactTxStreamer` (`gyges_chain::testing::FakeLightwalletd`, server side generated by `build.rs` from `proto/service.proto` onto the upstream message types, snapshotting a `FakeNode`'s chain) drives streaming into the cache in batches with the Tor tag, a skipped block, a fork, a hung stream and the reconnect after it, the subtree roots of every pool, the wrong chain, broadcasts, and `fill_cache` over both backends; `FakeNode` answers `z_getsubtreesbyindex` from configured roots. Facts recorded in `OVERVIEW.md` §4.4 (the `tor` gRPC path is gated behind `lightwalletd-tonic-tls-webpki-roots`, now enabled; TLS behaviour; `z_getsubtreesbyindex` and `SubtreeRoot` shapes). Not done: Tor bootstrap itself is untested until the nightly tier (TESTING.md §1); `GetAddressUtxos` (fourth M2 item). The scheduler's use of the backend and `GetInfo.tor` came with the second and third items.
- [x] Handoff validation at `retained_from + k` (tree roots, hash chain, subtree roots); endpoint trust state in `daemon status`. Landed as `gyges_core::handoff` (check 1: per pool, the tree size the wallet recorded for block `V` against the frontier size of `z_gettreestate(V)` and the wallet's ShardTree root over that many leaves against the frontier's root, Sapling, Orchard and Ironwood; check 3: `agreed_subtree_roots`, which refuses an endpoint root or completing height that differs from `z_getsubtreesbyindex` and keeps only the node-confirmed run for `put_*_subtree_roots`) and `gygesd::backfill` (check 3 when a session opens, before anything from the endpoint reaches the wallet; check 2 at every batch boundary against `getblockhash` and, at the handoff, on the wallet's recorded hashes at `V`, `retained_from` and the first backfilled block; a block the scanner refuses or an unlinked chunk fails too). A failed check truncates the key to the block before the backfill (`truncate_to_chain_state` where no block row exists, as for a restore's `birthday - 1`), drops the endpoint's cached rows, persists the untrusted mark in `<network>/fallback_trust.json` (kept across restarts, cleared by configuring another endpoint) and stalls the key with `UntrustedBackfill` (`STALL_REASON_FALLBACK_UNTRUSTED`). `GetInfo.fallback.trust` is `UNTESTED` / `VERIFIED` / `UNTRUSTED`, shown by `daemon status`; `GetInfo.tor` reports the endpoint's Tor client (`DISABLED` for `use_tor = false`, unset until the first backfill bootstraps it, which the CLI prints as `not started`). Not done: a lie that only makes the wallet's ShardTree refuse an insertion surfaces as a wallet error retried each tick rather than as `UntrustedBackfill` (the scan order makes this unlikely: a session scans from the scanned tip up before the node's frontier enters the tree); Tor itself is still untested until the nightly tier.
- [x] Pruning-race fallback (Case A → Case B) and `Stalled` states. Landed as the `Backfilling { via_tor, from, to }` state in `gyges_core::sync` and the session in `gygesd::backfill`: a key with `scanned_tip < retained_from` and an endpoint configured backfills from its scanned tip up (before upstream's queue sends it to the chain tip) to `V = min(retained_from + overlap_blocks, tip)`, one `cache.scan_batch` per tick through `gyges_chain::fill_cache` (rows tagged `tor-lwd`, evicted once scanned unless `cache.keep_historical`), with the prior tree state from the node where it still serves one and from the endpoint below that; the session is recorded in `keys/<id>/backfill.json` so a restart before the handoff still validates.
