# Gyges Roadmap

> Drafted 2026-10-20 from `OVERVIEW.md` §7. Milestones are ordered by risk retired per unit of work; each later milestone has its own design note before code starts.

## Principles

- **Core loop first.** Nothing ships until init → sync → send → confirm works end to end on regtest against a real `zakurad`. Everything else is layered on top of that loop.
- **Track Zakura deliberately.** Exact pins, `Cargo.lock` committed, one PR per upstream release, regtest suite green before merge (`OVERVIEW.md` Q-D3).
- **Pools are data.** Orchard, Ironwood and transparent spend in the MVP; Sapling receive-only. Ironwood cannot be "off": after NU6.3 (regtest height 1, mainnet 3,428,143) the wallet libraries build every shielded output in the Ironwood pool and the ZIP 318 turnstile keeps value out of Orchard, so Orchard is spend-only there (Q-D7, `OVERVIEW.md` §4.3).
- **Security claims are tested.** Every control in `THREAT_MODEL.md` names the test that proves it (`TESTING.md`).

Landed as `gyges_core::tx::{Owner, check_change}`, run in `sign` before any signature (for `pczt sign` and `tx send` alike) and at the start of `verify` (`BroadcastPczt`, `SendTransaction`). It does three things:
  1. It authenticates the output fields it reads. Every Orchard and Ironwood action's output must reproduce its note commitment from `recipient`, `value` and `rseed`, and its `cv_net` must match its values (upstream `verify_note_commitment`, `verify_cv_net`); every Sapling output likewise (`verify_note_commitment`, `verify_cv`). Missing fields fail closed. Without this, a file could commit to an attacker's note while its `recipient` field named the signer's change address: proving needs no secret, and the signature covers only the commitment.
  2. It binds every `user_address` label to the receiver its output pays (the UA's Orchard receiver, the Sapling address, the transparent script), so stolen change cannot be relabelled as a payment.
  3. It refuses every other non-zero output (change) the key does not own. `Owner` holds the account's UFVK and, where there is a wallet, its transparent receivers: an Orchard-protocol address in either scope of the Orchard FVK (Ironwood uses the same keys), a Sapling address its DFVK decrypts, a transparent script among the wallet's receivers or, without a wallet, at an external or internal index below `TRANSPARENT_CHANGE_SEARCH` (1,000).
