# Gyges Threat Model (`THREAT_MODEL.md`)

> **Status: reviewed 2026-10-21 against the M1 implementation.** Drafted from the proposals in `OVERVIEW.md` §6 (Q-S1…S7, Q-K7, Q-D5, Q-Y5, Q-O1); the S questions and Q-K7 were reviewed and decided on 2026-10-21, and each decision is recorded under its question in `OVERVIEW.md` §6. In §5 a checked box is an implemented control whose Proof column names the test that proves it; an unchecked box is a control planned for the milestone named in its row. §6 records the decisions taken on the draft's open questions and the four items that still need verification, each assigned to a milestone. Where this document disagrees with `ARCHITECTURE.md`, this document is the more recent statement of intent and `ARCHITECTURE.md` should be corrected.

## 1. Scope and Assets

Gyges is a two-process wallet: a daemon (`gygesd`) that holds all key material and chain state, and a CLI (`gyges`) that is a pure gRPC client over a Unix Domain Socket (UDS). The daemon talks to a Zakura node over JSON-RPC, optionally to an archival `lightwalletd`/`zaino` over Tor for historical backfill, and optionally to a Keystone 3 Pro over QR codes.

### 1.1 Assets, ranked by impact

| # | Asset | Where it lives | Impact if disclosed | Impact if tampered |
|---|---|---|---|---|
| A1 | **BIP-39 entropy** (32 bytes; the mnemonic is derived from it) | `keys/<id>/seed.age`, encrypted at rest (Q-S5); decrypted transiently in `gygesd` RAM for `key init`, `key export-seed` and unlock | Total loss of all funds of that profile, now and forever, on every chain the seed is used on | Irrelevant: a tampered seed simply fails to derive the known UFVK |
| A2 | **Unified Spending Key (USK)** | `gygesd` RAM only: derived from the entropy for one signing step, moved into the signing task and out of scope when it returns (Q-S3). The upstream `UnifiedSpendingKey` does not zeroize on drop (`zakura-keys` 4.0.0-rc2), so its bytes can linger in freed memory until reused (§6 item 10) | Total loss of funds of that profile | n/a |
| A3 | **Vault passphrase** | User's head; terminal input; one gRPC request field (`[debug_redact]`); never on disk | Equivalent to A1 while `seed.age` is also obtained | n/a |
| A4 | **Signing session token** (random 32 bytes, connection-scoped, Q-S1) | `gygesd` RAM. The shipped CLI never requests one: `key unlock` asks for daemon scope, which returns no token, and `tx send` uses passphrase signing sessions; the token exists for other clients of the API (§6 item 5) | Lets the holder sign with the unlocked key until the session ends; same connection only, so near-useless to a third process | n/a |
| A5 | **Unified Full Viewing Key (UFVK)** | `wallet.sqlite` `accounts` table; `profile.json` fingerprint; Keystone UR payloads | Complete, permanent visibility into all incoming and outgoing shielded activity of the profile; no spending ability | A substituted UFVK makes the wallet scan for someone else's notes; the profile would appear empty |
| A6 | **`wallet.sqlite` contents** (notes, nullifiers, memos, addresses, labels; from M3 `tex_queue`; from M5 Keystone `signing_sessions`. Passphrase signing sessions are memory-only, `API.md` §6.1) | `keys/<id>/wallet.sqlite`, plaintext at rest (Q-S6) | Full financial history, counterparties where memos reveal them, address set, pending payments | Could cause the wallet to build transactions against a false view of the chain; the Verifier role and node-confirmed anchors limit what this achieves (see §3, row 6) |
| A7 | **Proven, unsigned PCZTs** awaiting a signature | `gygesd` RAM for passphrase sessions, never on disk; `wallet.sqlite` `gyges_signing_sessions` for Keystone sessions from M5 (Q-K4) | Reveal the full transaction (recipients, amounts, memos) before broadcast | A modified PCZT is caught by the Verifier before broadcast (Q-K4, Q-K7) |
| A8 | **Block cache** (`cache/blocks.sqlite`, Q-Y3) | `~/.gyges/<network>/cache/` | The *range* of cached Tor-fetched blocks reveals the approximate birthday of restored keys | A corrupted cache yields `PrevHashMismatch` and a rescan; it cannot forge notes because tree roots are checked against the node (Q-Y5) |
| A9 | **Network metadata**: birthday height, requested block ranges, transparent addresses queried, broadcast timing and origin IP | Observable by the Zakura node, the archival endpoint, and the network path | Links the user to wallet activity; weakens shielded privacy | n/a |
| A10 | **Logs** (`logs/gygesd.<date>.log`, seven daily files; `logs/audit.log`, never rotated; Q-O1) | `~/.gyges/<network>/logs/` | Should contain heights, counts, key ids and timestamps only; any leak of A5–A9 into logs is a bug | n/a |

### 1.2 Security goals

1. **Confidentiality of A1–A3** against every adversary in §3 except those explicitly out of scope (§4).
2. **No unauthorised spend**: funds move only after an action the legitimate user took (passphrase entry or Keystone confirmation) *in the same CLI invocation* that initiated the spend, or in a deliberate `key unlock --timeout` window.
3. **Integrity of what is broadcast**: a transaction leaves the daemon only if its effects match the proposal the user saw.
4. **Integrity of the wallet's view of the chain**: no external data source can make the wallet believe in notes, nullifiers or tree states the local node does not confirm.
5. **Privacy**: no third party learns more than the Zcash protocol already exposes, and the user is told exactly what the archival endpoint and the node do learn.

## 2. Trust Boundaries

 └──────────────┘          └───────────────────┘   └───────────────┘

| Boundary | Crosses it | Control |
|---|---|---|
| **B1** CLI ↔ daemon | Passphrase (one field, zeroized, `debug_redact`), session token, UR frames, proposal summaries, events | Kernel-local UDS; `SO_PEERCRED` / `LOCAL_PEERCRED` uid check on every accept; connection-scoped sessions; per-key unlock rate limiting (Q-S1, Q-S2) |
| **B2** daemon ↔ Zakura node | Block requests, tree-state requests, raw transactions to broadcast, mempool polls | Cookie auth (HTTP Basic). The node is **trusted for consensus state** (tree roots, block hashes, anchors). It is not trusted with keys and it sees the wallet's full request pattern (Q-D2) |
| **B3** daemon ↔ archival endpoint (M2) | Block range `[birthday, retained_from + k]`, `GetSubtreeRoots`, optionally `GetAddressUtxos` | Tor circuit (prefer `.onion`); every result validated against the node's tree roots and hash chain before use; no hard-coded endpoint; endpoint marked `untrusted` on any mismatch (Q-D5, Q-Y5) |
| **B4** daemon ↔ filesystem | All at-rest assets | 0700 dirs, 0600 files, startup refusal on wider permissions; `seed.age` encrypted; `wallet.sqlite` relies on full-disk encryption (Q-S5, Q-S6, Q-S7) |
| **B5** daemon ↔ Keystone (via CLI terminal and camera; M5) | Redacted PCZT or batch request out; signatures or signed PCZT in | Redactor strips proofs, witnesses and the proprietary map but never amounts, recipients or memos; Verifier compares the result to the stored proposal before broadcast (Q-K4, Q-K7, Q-C6) |
| **B6** online daemon ↔ air-gapped daemon (M4) | `.pczt` files on removable media | Online side runs Verifier on the returned file exactly as for Keystone (Q-K5) |

## 3. Adversaries

Each row: what the adversary can *learn*, what they can *steal or cause*, which proposed control mitigates it, and what remains.

| # | Adversary | Can learn | Can steal / cause | Mitigating controls | Residual risk |
|---|---|---|---|---|---|
| 1 | **Same-user malware with socket access only** (can open `gygesd.sock`, read the user's files, but cannot `ptrace` or replace binaries) | Everything in `wallet.sqlite` (A5–A7): full history, memos, addresses, pending PCZTs. The encrypted `seed.age` bytes. Via RPC: balances, addresses, sync state. | Cannot spend: `UnlockKey` creates a session bound to *its own* connection, so it cannot ride on the user's open window (Q-S1). It can call `UnlockKey` itself and guess passphrases (rate-limited per key id, so reconnecting does not help, Q-S2). It can call `SendTransaction` and get as far as `SignatureRequired`, i.e. it can build and prove transactions but not sign them. It can abort or create signing sessions and pollute `tex_queue` state. It can exfiltrate `seed.age` for an offline passphrase attack. | Connection-scoped unlock and session tokens (Q-S1); passphrase rate limiting with exponential back-off (Q-S2); scrypt work factor ~1 s (Q-S5); no `--json` path for seed export and `vault.allow_seed_export = false` (Q-S4); audit log of every unlock, session and broadcast (Q-O1) | **Total loss of privacy for the profile.** Offline brute force of a weak passphrase. Denial of service (session spam, abort of in-flight ZIP 320 steps while `built`). The hardened deployment (dedicated `gygesd` user, 0660 socket with a `gyges` group) removes file access and leaves only the RPC surface. |
| 2 | **Same-user malware that can `ptrace` the daemon or replace `gyges`/`gygesd`** | Everything, including the USK while a session is open and the passphrase as it is typed | Everything | None by design; the hardened deployment (different uid) converts this into adversary 3 | **Out of scope** (§4). Documented honestly rather than mitigated. |
| 3 | **Another local user** on the same machine | Nothing from `~/.gyges` (0700). Process list shows that `gygesd` runs and for which network. | Nothing. Cannot connect to the socket (`SO_PEERCRED` uid check, 0600 mode). | Peer-credential check, directory and socket permissions, startup refusal on wider permissions (Q-S1, Q-S7) | A root user is adversary 2. Shared `/tmp` or world-readable backup tarballs created by the user (`key backup`) are the user's responsibility; the docs must say so. |
| 4 | **Stolen laptop, powered off** (attacker has the disk) | With full-disk encryption: nothing. Without it: everything in row 1 plus `seed.age` for offline attack. | Without FDE: offline brute force of the passphrase; with a weak passphrase, total loss. | `seed.age` with scrypt ~1 s (Q-S5); 32-byte entropy, not the derived seed, so there is no second secret to protect; `profile.json` records the scrypt parameters so they can be raised by migration | **`wallet.sqlite` is plaintext.** v1 explicitly relies on OS full-disk encryption for A6 (Q-S6). SQLCipher with an OS-keychain key is the proposed later mitigation. The passphrase strength is the only barrier to A1. |
| 5 | **Stolen laptop while unlocked** (screen unlocked, user session live) | Everything in row 1 via the CLI or the files | If a `key unlock --timeout` window is open on a still-connected CLI session: can spend until the TTL expires, by using that CLI's shell. The inline-unlock path holds the USK only across the signing step (Q-S3), so an interrupted `tx send` leaves nothing unlocked. | Short default TTL (`vault.unlock_ttl = "5m"`), idle timer, `key lock --all`, USK dropped immediately after signing in the inline flow (Q-S3); sessions die with the connection (Q-S1) | A user who runs `key unlock --timeout 8h` for a batch job has chosen to accept this. The docs should warn and the audit log records it. Adversary can also exfiltrate `seed.age` (becomes row 4). |
| 6 | **Malicious or buggy Zakura node** | The wallet's complete request pattern: every block fetched (hence the scan position of each key), every `getrawtransaction`, every broadcast and its timing, transparent address queries where used. Not the UFVK, not note contents. | Can feed false tree states and block data. Consequences: (a) wallet builds a transaction against a false anchor, which the *real* network rejects, i.e. denial of service; (b) withholds blocks so the wallet never sees incoming notes or a spend of its own notes (stale balance); (c) lies about `pruneheight` to force a Tor backfill and learn the birthday from the endpoint it does not control, or to prevent one; (d) drops or delays broadcasts; (e) reports a transaction as mined when it is not. | None against a trusted node by design: the node is the root of trust for consensus state (§2, B2). `sync status` exposes chain tip and hashes so a user can cross-check against another node. ZIP 317 and deterministic proposals mean the node cannot inflate fees. The daemon warns once, at the first successful poll, when `zakura_rpc.url` is not this machine (§6 item 12). Broadcast over Tor (`--via-tor`, `broadcast_via_tor`) decouples broadcast origin from the node; it is refused rather than downgraded when no Tor endpoint is configured (`gygesd/tests/rpc.rs::via_tor_broadcasts_through_the_fallback_endpoint_and_never_falls_back_to_the_node`). | **The node is trusted.** A user who does not run their own node has moved this adversary into the trusted base. The documents must state that Gyges is designed for a *local* Zakura node, and that a remote node operator sees everything in the "can learn" column. Detecting an eclipsed or lying node is out of scope for v1. |
| 7 | **Compromised archival lightwalletd / zaino** (Case B backfill over Tor) | The requested block range, hence the approximate birthday of the restored key; the fact that *someone* is restoring; any transparent addresses queried via `GetAddressUtxos` for transparent recovery. Not the origin IP (Tor), not the UFVK. | Attempts: omit blocks (hide incoming notes), inject or reorder commitments (corrupt witnesses so the wallet cannot spend, or desynchronise it from the real tree), serve a fork, hang the stream (DoS), return fake transparent UTXOs. | Stream overlaps the node's window by `k = 10` blocks and is validated at `V = retained_from + k`: (1) Sapling and Orchard tree roots and leaf counts from `z_gettreestate(V)` must match the ShardTree built from the stream; (2) `prev_hash` chain must link and `getblockhash` must match at `V` and `retained_from`; (3) `GetSubtreeRoots` must equal `z_getsubtreesbyindex`. On failure: truncate the key to its birthday, mark the endpoint `untrusted`, refuse further backfill until the config changes (Q-Y5). No hard-coded endpoint; explicit user consent before the first backfill; `.onion` preferred (Q-D5). | An omitted or forged *shielded* output changes the tree root and is caught. **Transparent history below `retained_from` cannot be root-checked**; each returned UTXO's transaction is fetched and its inclusion verified against a node-confirmed block hash, which prevents fabricated UTXOs but not *omitted* ones. Timing and range leakage is inherent and documented. DoS is accepted. **Needs verification (M2):** that `z_getsubtreesbyindex` works for pruned ranges on a pruned node (Q-Y5 expects so; the commitment tree is consensus state). |
| 8 | **Compromised or buggy Keystone device** | Everything in the redacted PCZT it is shown: recipients, amounts, memos, the wallet's Orchard actions. It already holds the seed, so key secrecy is not the concern. | Returns signatures for a *different* transaction than displayed (e.g. altered recipient or amount), or a malformed result. | Daemon never trusts the returned payload: Combiner rejects structurally different PCZTs; the **Verifier** role re-checks every output, amount, fee and anchor against the *stored* proposal before Spend Finalizer and Tx Extractor run (Q-K4, Q-K7). The host keeps the proven, unredacted PCZT and applies only the signatures. | A device can refuse to sign (DoS). A device that signs correctly but exfiltrates the seed through side channels is a hardware-wallet problem outside this document. The device sees memos; users who do not want that should not use memos with Keystone. |
| 9 | **Compromised host when signing with Keystone** (the host is adversary 1 or 2, the device is honest) | Everything the host holds (rows 1–2). | Presents the device with a PCZT whose recipient or amount differs from what the user intended. The device display is the only defence. | The Redactor strips proofs, witnesses and the `gyges.*` proprietary map but **must never strip amounts, recipients or memos** that the device displays; `ARCHITECTURE.md` §3.4 must list the redacted fields exactly. `tx send` prints the same summary the device shows so the user can compare (Q-K7). The device refuses transactions it cannot fully display. | The user must actually read the device screen. A host can still DoS, leak metadata, and substitute the destination for a *shielding* transaction the user does not inspect carefully. **Needs verification (M5):** which PCZT fields the current Keystone firmware displays, so the summary matches the device exactly. |
| 10 | **Network observer on the Tor path** (exit node, Tor directory authorities, ISP, archival endpoint's upstream) | That a Tor client bootstrapped from the user's IP (ISP); that *some* Tor user fetched Zcash blocks from the endpoint (exit node, unless `.onion`). With TLS to the endpoint, not the content. Broadcast over Tor: the raw transaction (public anyway), not its origin. | Traffic correlation between the user's Tor bootstrap and the endpoint's incoming connection, in principle. Blocking Tor (DoS). | Tor via `arti-client`; `.onion` endpoints preferred so no exit node exists; TLS (`rustls`, webpki roots) to clearnet endpoints; `broadcast_via_tor` option for the final transaction (Q-D5) | Tor's own threat model applies: a global passive adversary can correlate. Users on networks that block Tor fall back to `use_tor = false` and become visible to the endpoint directly, which the config must make loud rather than silent (`gygesd` warns at start). *Verified (M2, `OVERVIEW.md` §4.4):* the `tor` gRPC path of `zakura-client-backend` 0.1.0-rc9.1 uses rustls with the webpki roots and the URI host as SNI for `https://` endpoints, no `danger_accept_invalid_certs`-style switch exists, and an `http://` clearnet endpoint is refused by `Config::validate` outside regtest, so only `.onion` endpoints go without TLS. The direct transport applies the same TLS configuration. |
| 11 | **Malicious `.pczt` file in the air-gapped flow** (removable media tampered between the online and offline machine, in either direction) | Online → offline: the attacker sees the unsigned transaction (recipients, amounts, memos, note witnesses, i.e. A7). Offline → online: the signed transaction. | Online → offline: substitute recipients or amounts so the offline signer signs an attacker's transaction. Offline → online: substitute a different signed transaction for broadcast; or inject proofs that do not verify. | Offline side: `pczt inspect` and `pczt sign` display the full effects and require confirmation; the signer holds the seed, so it can derive its own addresses and refuse an unknown change output (verified: the upstream Signer role does not check change ownership, so `pczt sign` does it, M4; §6 item 8). Online side: Verifier against the stored proposal before broadcast, so a substituted signed transaction is refused (Q-K5, Q-K4). `combine` refuses PCZTs whose embedded `gyges.key_id` differ (Q-C6). | The offline user must read the `pczt sign` summary as carefully as a Keystone screen; there is no device-enforced display. A substituted file that matches the stored proposal exactly is by definition the intended transaction. The attacker learns A7 in transit; encrypting `.pczt` files at rest on the media is a possible later addition. |

## 4. Out of Scope

These are stated so that nobody mistakes silence for a guarantee.

- **Keyloggers or screen capture on the host.** The passphrase is typed into a terminal; anything that can read it before `rpassword` does defeats the vault.
- **A replaced or trojaned `gyges` or `gygesd` binary**, or a modified Rust toolchain. Release signing and provenance (Q-O5) address distribution, not a host that is already compromised.
- **Kernel, hypervisor or firmware compromise**, including anything that can read `gygesd` memory or `ptrace` it as the same uid without the user noticing. `secrecy`/`zeroize` limit the *window*, not the *possibility*.
- **Physical attacks on the Keystone device**, fault injection, supply-chain substitution of the device, or Keystone firmware vulnerabilities. The device is treated as a black box that either behaves or is detected by the Verifier.
- **Memory-disclosure side channels** (Spectre-class, cold boot, swap). The daemon should request `mlock` for `SecretBox` pages where the platform allows it, but this is a hardening step, not a boundary.
- **Windows.** Named pipes, ACLs and the absence of `SO_PEERCRED` make §2 and §3 rows 1–3 different; a separate design note is required before support is claimed (Q-O4).
- **Remote daemons.** The design assumes the UDS and the daemon are on the user's own machine. Forwarding the socket over SSH is possible but extends boundary B1 across the network and is not analysed here.
- **The Zcash protocol's own privacy limits**: transaction graph analysis of transparent components, amount and timing correlation of deshielding steps (ZIP 320 Step 1 → Step 2 is visibly linked on-chain by design), and anything a `tex1` recipient learns from the ephemeral address.
- **Consensus bugs in Zakura** or in the upstream `librustzcash` crates. The entire stack is pre-release (§4 of `OVERVIEW.md`).

## 6. Decisions on the Draft's Open Questions

The twelve questions the first draft could not close, with the decision taken on 2026-10-21 or the milestone that will verify the fact. Numbering is kept so that references elsewhere stay valid.

1. **Sapling proof generation key handling (Q-K3).** *Implemented (ROADMAP.md M6, first item).* Sapling spending is for `local-seed` profiles only. A proposal with Sapling inputs is unlocked before proving, the Updater inserts `proof_generation_key`, and the PCZT is proven and signed inside the one `SendTransaction` stream that created it; nothing with a proof generation key in it is ever written to disk. Keystone and watch-only profiles have no `sapling` in `spend_pools`, so the question never arises for them. As built: each spend's key is chosen by recomputing the note's nullifier under the account's external and internal keys (internal change needs the internal `nsk`), and a spend neither reproduces is refused; `pczt create` leaves Sapling notes out and `pczt prove` / `pczt sign` refuse a Sapling spend, so no file ever needs the key; `rpc.rs::sapling_notes_are_keyed_proven_and_signed_inside_the_send_stream` searches every file under the daemon's home for both scopes' `nsk` after the sends and finds neither.
2. **Runtime CPU feature detection for the `*-asm` features (Q-D6).** *Still needs verification (M6).* Read in the crate source whether `zakura-pasta-curves` checks for BMI2/ADX at runtime before the `perf` feature becomes the release default.
3. **`wallet.sqlite` at rest (Q-S6).** *Decided.* v1 relies on OS full-disk encryption plus `0700`/`0600`, stated in §3 row 4. SQLCipher is an M6 option with the database key held by the OS keychain only; it is never wrapped by the vault passphrase, because the daemon must scan while the vault is locked.
4. **Hardened deployment ergonomics (Q-S1).** *Decided.* The hardened mode is documented, and the two pieces it needs are implemented: `daemon.socket_group` (socket `0660`) and `daemon.allowed_uids` (the interactive user's uid, admitted at accept time and in the policy layer). First-class tooling (`gyges daemon install --hardened`) is M6; until then `key init` and `key backup` through a dedicated-user daemon are done over the socket by an allowed uid.
5. **Session token transport.** *Resolved.* `UnlockKeyRequest.scope` makes the two modes explicit: `DAEMON` returns no token and creates an idle-timer unlock any admitted client may use; `CONNECTION` returns a token bound to that socket connection. The shipped CLI never requests `CONNECTION` (`key unlock` asks for `DAEMON`; `tx send` and `tx shield` send an empty `session_token` and use passphrase signing sessions), never reads `session_token` from a response and so cannot print it, in `--json` or otherwise. Connection tokens are an API-level mechanism for other clients, tested over the socket in `rpc.rs`.
6. **Rate limiting across connections.** *Resolved.* The back-off is keyed on the key id inside `VaultManager::verify_passphrase`, shared by `UnlockKey`, `ExportSeed` and the session path; `rpc.rs::wrong_passphrases_are_rate_limited_per_key` reconnects and is still limited.
7. **Keystone display coverage (Q-K7).** *Still needs verification (M5).* On hardware: which PCZT fields the Cypherpunk firmware displays, whether it shows memos, and how it shows the ZIP 320 Step 2 transparent-only transaction. `tx send --to tex1…` stays disabled for Keystone profiles until then (Q-K1).
8. **Air-gapped change-output verification (§3 row 11).** *Verified.* The upstream `pczt` Signer role (`zakura-pczt` 0.1.0-rc7) does not check that change outputs belong to the signer; its documentation tells the caller to confirm change amounts before signing. `pczt sign` in M4 therefore decrypts every shielded output with the signer's own keys and matches transparent outputs against its own addresses, and shows any output it cannot claim as a payment for the user to confirm. *Landed (`ROADMAP.md` M4, third item):* `gyges_core::tx::check_change`, at sign time and before broadcast, first checks every shielded output's `recipient`, `value` and `rseed` against its note and value commitments (a file can otherwise name the signer's change address while committing to an attacker's note), then checks every address label against the receiver the output pays, and refuses change the key does not own; tested by `gygesd/tests/rpc.rs::redirected_change_is_refused_at_sign_and_at_broadcast`, including a swapped `cmx` under an unchanged change address (signed before this item) and property tests at sign and at broadcast.
9. **Transparent recovery below `retained_from` (Q-Y5).** *Decided.* No second endpoint. Every restore whose birthday is below `retained_from` prints, and `daemon status` repeats, that transparent history below the retention height is best-effort because omitted UTXOs cannot be detected (M2).
10. **`mlock` and core dumps.** *Decided.* `gygesd` sets `RLIMIT_CORE` to zero (soft and hard) before anything else, so a crash never writes key material to disk; a platform that refuses is reported once and the daemon still starts. No `mlock`: `secrecy` has no locked allocator, and swap is covered by the full-disk-encryption assumption of item 3. *Residual, needs an upstream change:* `UnifiedSpendingKey` in `zakura-keys` 4.0.0-rc2 does not zeroize on drop, so the derived key's bytes can remain in freed memory after the signing task; only the 32-byte entropy is zeroized. Raise upstream; not a boundary (§4).
11. **Log retention and the audit log as an asset.** *Decided.* `audit.log` is never rotated and holds key ids, event names and timestamps only. Under adversary 1 that adds nothing to what `wallet.sqlite` already reveals, and the file is the only record that survives a wallet wipe, so it is kept whole; a user who wants less history truncates it. The seven daily `gygesd.<date>.log` files carry heights and counts only.
12. **Remote-node mode.** *Decided.* Gyges is designed for a local node; a remote one is allowed but loud: when `zakura_rpc.url` is neither `localhost` nor a loopback address the daemon warns at the first successful poll that the node's operator sees every block fetched, every broadcast and its timing (§3 row 6). No `allow_remote_node` flag and no Tor for node RPC.
